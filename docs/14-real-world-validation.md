# 14 — Real-world validation: scale and older Minecraft versions

Parity and performance beyond the small golden fixtures: one real-scale survival world and vanilla worlds from older
Minecraft versions, each rendered by Java BlueMap 5.28 and by our `bluemap` from copies of the same config.
Scripts: `tools/real_world.py`, `tools/accept_versions.py` (usage in their headers).

## Hardware and setup

- **testbox**: Intel Xeon E-2136 (6 cores / 12 threads, 3.3 GHz), 31 GiB RAM, Linux 6.8, data on md RAID over two
  7200 rpm HGST HDDs. It is a shared machine. Renders ran under `flock ~/bench.lock`, but other users' processes
  (one core of an unrelated job, at times a `rustc`) still ran alongside. CPU seconds are the robust figure and wall
  times are indicative.
- Java: Temurin 25.0.4.1, BlueMap CLI 5.28, default JVM flags (max heap = ¼ of RAM ≈ 8 GiB).
  Ours: release build of `master` @ `8be0570` (glibc, `cargo build --release`) and the static musl build from
  `tools/build_core.py linux-x64` (cargo-zigbuild).
- Both sides use one config folder created by Java (`render_serve.configure`), with `render-thread-count: 12`, the
  default map settings and file storage (gzip). Each run starts from an empty storage (`-r -f`).

## 1. Real-scale world (MC 26.3)

**World.** `fixtures/real`: the vanilla seed (`bluemap_reverse`) over 4096×4096 blocks (−2048…2047), generated by the
26.3 vanilla server with `real_world.py gen`. Batches of 32×32 chunks are force-loaded three at a time, each released
once every chunk tests `execute if loaded`. Generation took 522 s with `sync-chunk-writes=false`. With the default
(true), an fsync per chunk on the HDDs would have stretched the final save to hours, so that run was aborted. Result:
654 MiB, 100 region files, 79,524 chunks. 67,600 of them have status `minecraft:full` (the 65,536-chunk area plus the
generated ring around it), and all of those carry `SkyLight`. The rest are the server's partial ring
(`structure_starts`, `biomes`, `terrain`, `initialize_light`), the same mix any real world has at its border.
`real_world.py verify` prints these counts.

**Parity.** Hires output is identical (16,641 tiles, byte-identical after decompression), as are listing, json and
rstate (36 tile-state, 16 chunk-hash and 4 region cells, all equal). Against Java's first render, the two sides differ
in exactly one place: a 3×11 pixel hole in Java's lowres, which also changes 2 pixels at LOD 2 and 1 at LOD 3.

| comparison (golden → candidate) | hires | lowres | rstate / json |
|---------------------------------|-------|--------|---------------|
| Java → ours (glibc) | 16,641/16,641 identical | LOD1 143/144, LOD2 15/16, LOD3 3/4 (one hole, below) | identical |
| Java → ours (static musl) | identical | same single difference | identical |
| Java → ours optimized, converted back to compat | identical | same single difference | identical |
| Java `-r` after edits → ours `-r` after edits | identical | same single difference (carried over) | identical |
| Java render 3 → ours (glibc) | identical | LOD1 143/144 (Java's 1984-pixel loss below), LOD2–3 identical | identical |

Every lowres pixel of ours equals at least one of the two compared Java renders. Each Java render misses pixels that
the other Java render and ours both have.

The hole is in `tiles/1/x-4/z-2.png`, pixels x 495–497 and rows 490–500 of both halves: blocks x −1505…−1503 and
z −510…−500. Java leaves it at alpha 0, as if never written. Ours has the terrain the identical hires tile (−48,−16)
holds there: grass and leaves at heights 63–80. The hole covers the last 3 columns of that hires tile, inside its
data, and crosses a chunk border (−1505 | −1504), so no tile, chunk or region edge explains it. **This is Java losing
writes, not a quirk we fail to copy.** The next two Java renders of the same config (`real_world.py render java2
--java -n 2`) produced the pixels, and the final one equals ours in that tile pixel for pixel. That same Java render
lost a different set of writes instead. In `tiles/1/x5/z-4.png`, 1984 metadata pixels (x 0–61, rows 402–433) are
missing: blocks x 2500–2561, z −1598…−1567, the lowres columns of two hires tiles over the `structure_starts` ring
outside the area. Java run 1 and ours have them, and they match. Java render 1 vs Java render 3:
`real_world.py compare java java2`, 2 LOD1 tiles differ. The 1.20.1 fixture showed the same loss (§2).
The probable mechanism is Java's lowres tile cache. Tiles live in weak and soft Caffeine caches, and `set()` holds only
a read lock (docs/03 §4). If a tile instance is dropped and reloaded while a render thread still writes into the old
instance, those writes are never saved. That fits the shape of the hole: a run of columns from one hires tile, on a
busy JVM. Ours keeps a single writer per lowres tile (`LowresStore`), so it cannot lose writes this way.

**Benchmarks** (forced render `-r -f` from an empty storage, 12 render threads, the same config):

| side | runs | wall s (median, range) | CPU s (median, range) | peak RSS MB (median) | output |
|------|-----:|-----------------------:|----------------------:|---------------------:|--------|
| Java 5.28 | 3 | 1413 (1316–1458) | 9843 (8307–9851) | 2139 | 1,544.9 MiB, 16,865 files (compat) |
| ours, glibc | 3 | 77.0 (67.8–85.5) | 471.6 (455.4–474.9) | 764 | 1,576.0 MiB, 16,865 files (compat) |
| ours, static musl | 1 | 65.9 | 598.9 | 611 | 1,576.0 MiB (compat) |
| ours, glibc, `format: optimized` | 1 | 49.2 | 498.3 | 802 | 309.6 MiB, 306 files |
| ours, optimized → compat conversion | 1 | 27.4 | 261.2 | 514 | 1,576.0 MiB |

Raw lines: `docs/results/bench.jsonl`, labels `real-*`. Java ran 08:41 UTC (run 1) and 09:53–10:38 (runs 2–3).

- Ours renders the same output with 20.9× less CPU and 18.4× less wall time, at 36% of Java's peak RSS (medians).
  Java's CPU is real work, not a lock convoy: it averaged 7.0 of 12 threads busy, at times 10.75 (`top`). The convoy
  docs/10 measured on the 22-thread PC did not show up here.
- The musl build is one run only. It used 27% more CPU than glibc for the same output; the allocator is the likely
  cause (docs/13 has the allocator benchmark). Its wall time sits inside glibc's run-to-run spread.
- **Optimized storage**: 309.6 MiB in 306 files, against 1,576 MiB in 16,865 files for compat: 5.1× smaller, 55× fewer
  files. The lowres PNGs are the same in both formats, so the hires-only ratio is higher. Rendering straight to
  optimized took 49 s wall. Converting it back to compat (`--convert-storage file --to compat`) took 27 s, and the
  result compares exactly like the direct compat render.
- **Optimized storage since BMQ3** (docs/17, run 2026-10-09, labels `real-rs-bmq3*`): **133.4 MiB** in 306 files,
  11.8× smaller than compat; the hires bundles went from 299 to 122 MB on disk. Converted back to compat it is the
  same 1,576.0 MiB in 16,865 files and compares to Java like the direct compat render: hires and rstate identical,
  the one known lowres difference. That run shared the box with a saturated disk (125 s wall, 282 s CPU, 873 MB),
  so its timings are not comparable with the table; the table's optimized rows are the BMQ2 run.
- Compat output: Java 1,544.9 MiB, ours 1,576.0 MiB, the same 16,865 files. Hires bytes match after decompression,
  but the gzip streams themselves differ.

**Incremental update.** `real_world.py edit` opens a copy of the world in the server and builds at 5 spots: a 48×48
glass roof at y 140, a 16×16×71 air shaft, a hollow gold-block tower and a torch. It saves, and 320 chunks in 6 region
files get new timestamps. Each side then runs `-r` (not forced) over its own full render, pointed at the edited world:

| | wall s | CPU s | peak RSS MB |
|-|-------:|------:|------------:|
| Java 5.28 `-r` | 20.5 | 155.1 | 712 |
| ours `-r` | 5.0 | 5.6 | 543 |

Both times include the fixed startup cost: resource loading, plus JVM warm-up for Java. Both outputs are identical
apart from the hole carried over from the full render, so the edited tiles match exactly.

## 2. Older Minecraft versions

BlueMap 5.28 renders worlds from MC 1.13.2 onward. `-v <mc>` selects the client jar used for resources:
`max(mc, 1.13)` for the resource pack and `max(mc, 1.19.4)` for the data pack, so a 1.16.5 map loads both the 1.16.5 and
the 1.19.4 client (docs/02 §1). For each version, that version's vanilla server (Java 8/17/21 from Mojang's metadata)
generated the `vanilla` fixture: 256×256 blocks, seed `bluemap_reverse`, force-loaded, plus the server's own partly
generated ring (`structure_starts`, …) around it. Java 5.28 rendered it with `-v <mc>`. Ours rendered a copy of the
same config, and `bm-golden compare-webroots` compared the two outputs. A second run of ours over Java's webroot
checked drop-in.

| MC | chunk format | hires tiles | hires | lowres (LOD 1–3) | rstate / json | drop-in `-r` renders |
|----|--------------|------------:|-------|------------------|---------------|---------------------:|
| 1.16.5 | pre-1.18 (2 client jars) | 181 | identical | identical | identical | 0 |
| 1.20.1 | 1.18+ | 145 | identical | identical vs 3 fresh Java runs (*) | identical | 0 |
| 1.20.4 | 1.18+ | 145 | identical | identical | identical | 0 |
| 1.21.1 | 1.20.5+ | 81 | identical | identical | identical | 0 |
| 1.21.4 | 1.21.4 | 90 | identical | identical | identical | 0 |
| 1.21.11 | 1.21.x | 81 | identical | identical | identical | 0 |

(*) The first Java render of 1.20.1, the golden one, differed from ours in one LOD 1 tile, `tiles/1/x-1/z1.png`.
Only the bottom (metadata) half differed: 6580 pixels, x 0–469, rows 0–13, alpha 0 in Java and 255 (no data) in
ours. Those pixels are the lowres columns of hires tiles z=15, x −16…−2, which sit over `structure_starts`-only chunks
at the world's edge. Java wrote neighbouring tiles' pixels in the same rows, so it dropped these writes. Three fresh
Java renders of the same config (`work/jrerun`) all match ours byte for byte (`compare-webroots`: IDENTICAL). The
golden render ran while the testbox's disk was saturated (another server's save plus world generation), so the
probable cause is upstream lowres updates getting lost under load, a nondeterminism in Java. Our renderer has no such
problem. Repro: `py -3 tools/accept_versions.py 1.20.1 --rerender` under heavy I/O. On an idle box it passes.

`accept_versions.py 1.20.1 --rerender` on the quieter box then passed every check. All six versions are identical to
Java, including the 1.16.5 path that loads two client jars. Ours renders the same `-v` handling, chunk formats
(pre-1.18 sections, 1.18+ palettes, 1.20.5+ and 1.21.x) and older resource packs without differences. The real
world's Java run showed the same class of lost lowres write (§1), so a single lowres-only difference against one Java
render should be rechecked against a second Java render before it counts as ours.

## Caveats

- One world seed and one size at scale; worlds are vanilla-generated, never player-built, apart from the scripted edits.
- The testbox is shared and HDD-backed; wall times include disk contention. Peak RSS is `ru_maxrss` (Java's
  includes its committed heap, which sizes itself to the machine).
- The older-version fixtures are small (256²), so they test format and resource handling, not throughput.
