# Devbox benchmarks, 2026-10-28

The README / docs/14 / docs/18 / docs/22 benchmarks run again on a faster machine with NVMe storage, Java BlueMap
included, so the ratios compare both renderers on one machine.

- **Machine (devbox):** AMD Ryzen 7 9700X, 8 cores / 16 threads, up to 5.5 GHz, 62 GB RAM, NVMe RAID 1 (`md3`).
  Shared with other projects; the 1-minute load around runs was 2–8 from other users, plus the job's own threads.
  Each run logged its load (`BGLOAD`/`LOAD` lines in the raw logs).
- **Build:** bluemap-rs `eb1d73c`, synced as `a124561`. The glibc build is `cargo build --release`; the static musl
  build matches `tools/build_core.py linux-x64` (the shipped core). Java is BlueMap 5.28 CLI on the repo's JDK 25,
  as in docs/14.
- **World and config:** the docs/14 4096² real world and config, copied from the testbox. Fixtures and outputs were
  on the NVMe, not tmpfs.
- **Raw data:** `bench.jsonl` (labels `real-d*`, `real-j*`, commit `a124561`). The devbox job logs are in
  `~/.testbox/devbench/` and the scripts in `~/devbench-scripts/`.
- Testbox numbers for comparison come from docs/14 (Xeon E-2136 6c/12t, HDD; bluemap-rs 2026-10-28, Java
  2026-10-08).

## Full render, `-r -f`, 4096²

Medians of 3 interleaved rounds (range in brackets), except Java at 16 threads (1 run).

| 12 render threads | Wall s | CPU s | Peak RSS MB | Output |
|---|---:|---:|---:|---:|
| Java 5.28 | 340.3 (339.9–344.3) | 4523 (4427–4588) | 2899 | 1,544.9 MiB |
| ours, glibc, compat | 14.8 (14.2–16.6) | 164.9 (163.8–176.9) | 858 | 1,576.0 MiB |
| ours, static musl, compat (shipped) | 16.0 (15.4–20.6) | 180.3 (177.3–199.4) | 711 | 1,576.0 MiB |
| ours, glibc, `format: optimized` | 12.4 (11.7–24.2) | 138.8 (134.4–141.3) | 909 | 130.4 MiB, 387 files |

| 16 render threads | Wall s | CPU s | Peak RSS MB |
|---|---:|---:|---:|
| Java 5.28 (1 run) | 272.3 | 4009 | 3313 |
| ours, glibc, compat | 14.8 (14.4–16.4) | 195.7 (191.0–196.1) | 1053 |
| ours, static musl, compat | 16.4 (14.9–22.2) | 211.5 (209.9–214.2) | 838 |
| ours, glibc, optimized | 13.9 (12.9–17.7) | 159.1 (149.1–163.4) | 1091 |

- **Same-machine ratios at 12 threads, glibc compat:** 23× faster, 27× less CPU, 30% of Java's peak memory. With
  optimized storage: 27× faster and 33× less CPU. On the testbox the same ratios were 24×, 31× and 41%.
- **Testbox → devbox:** bluemap-rs compat goes 57.9 → 14.8 s wall (3.9×) and 320 → 165 s CPU. Optimized goes 25.1 →
  12.4 s and 263 → 139 s. Java goes 1413 → 340 s and 9843 → 4523 s. Both gain more wall time than CPU: the testbox
  HDD costs wall time on its own, and so do the testbox's slower cores.
- **16 threads don't help bluemap-rs.** Wall time is unchanged, CPU rises 13–19% (SMT siblings on 8 cores) and peak RSS
  rises ~20% (one set of mesh buffers per thread). Java does gain at 16 threads (340 → 272 s). Its 12-thread run has
  a serial share that the extra threads hide.
- **Peak RSS** is ~2% lower than on the testbox at 12 threads (858 vs 878 MB): same allocations, different page-cache
  and allocator slack.

## Tile serving (docs/18 harness)

Medians of 3 runs at 15:2x UTC (job `web3`). busy_cpus from other users was 0.2–0.8 before each run. Tiles/s are at
32 connections; ranges in brackets.

| Storage, client | CPU ms/tile, 1 conn (devbox / testbox) | Tiles/s, devbox | Tiles/s, testbox | KB/tile |
|---|---:|---:|---:|---:|
| compat | 0.03 / 0.09 | 150,515 (140,988–159,154) | 50,588 | 96 |
| optimized, browser unpacks, zstd | 0.02 / 0.06 | 328,215 (251,445–328,453) | 102,843 | 7 |
| optimized, browser unpacks, gzip | 0.24 / 0.45 | 32,076 (21,830–32,612) | 14,372 | 8 |
| optimized, no unpack script, zstd | 1.51 / 3.04 | 4,218 (4,152–4,370) | 1,750 | 96 |
| optimized, no unpack script, gzip | 3.24 / 7.04 | 2,322 (2,272–2,331) | 1,019 | 96 |

- **Optimized vs compat:** with the browser unpacking, optimized serves 2.2× as many tiles per second as compat, the
  same ratio the testbox gave (2×). A first, single run at 12:5x under other users' load (busy_cpus 5.2) gave
  140,260 / 178,064 / 9,712 / 3,217 / 1,873 tiles/s. The optimized rows lose the most under contention: they
  spend more of their time in CPU work per tile.
- **Clients without the unpack script** cost 1.5–3.2 ms of server CPU per tile, about 50–100× compat's. That is the
  case a server-side unpack cap would bound.

## Cold first read of a bundle (docs/22 bench, 32 threads, page cache evicted)

| World | Bundles | Cold req/s (3 runs) | Cold p99 | Testbox HDD |
|---|---:|---:|---:|---|
| 4096² (d12-opt output) | 81 | 9,408–10,017 (2 runs logged in full) | 0.7–8.4 ms | 98 req/s, p99 0.86 s (k=8) |
| k=8, 32768² (`tools/scale_world.py`) | 4096 | 32,398–66,163 | 0.9–6.1 ms | 98 req/s, p99 0.86 s |

- **NVMe vs HDD:** the cold first touch is 330–675× faster in req/s on NVMe. The sidecar index makes it one 2 KB read
  per bundle.
- **Warm and hot paths** run at 1.0–3.2 M req/s, p50 3–5 µs.
- **The k=8 render** was not timed on the testbox, so it has no comparison here.
